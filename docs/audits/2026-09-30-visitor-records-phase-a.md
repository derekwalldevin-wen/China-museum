# 访客实地记录（第一期：本地记录 + 导出）

日期：2026-09-30。状态：**已实现并上线（本地记录阶段）**。目标态：审核后公开展示。

## 一、为什么单独做一层

华夏博物志的策展层有一条硬规矩：每张图都有授权记录（`images.json` 的 `license/licenseUrl/assetSha256` 缺一不可），每条事实都有来源，AI 图必须打标。访客上传同时带来四个新问题——图片授权无法自动核实、地点与器物名多为访客自述、需要内容审核、以及首屏性能预算（入口 JS 只剩几百字节余量）。

因此访客内容被定为**第四类**（与「器物事实／研究推断／当代传播」并列）：**访客投稿 · 未经馆方核验**。它只作为线索，永不自动进入策展数据；要"补充"进站必须由站长升级并补一条来源。

## 二、本期做了什么（无需后端、不产生任何上传）

新增独立页面 `/visitor-records/`（Vite 第二个入口，与舆图互不加载）：

| 能力 | 说明 |
| --- | --- |
| 新增记录 | 博物馆名称（必填）、省份（34 项固定列表）、城市（必填）、参观年月（可选）、文字说明（≤500 字） |
| 照片处理 | 每张图在**浏览器内**重新编码：长边 ≤2048、JPEG q82，另生成 ≤480 缩略图；**重编码即剥离 EXIF/GPS** |
| 上限 | 每条 ≤12 张；单张源文件 ≤12 MB；非图片或超限会给出具体原因 |
| 同意项 | 必须勾选「本人拍摄、拥有版权、馆方允许拍摄」与「同意审核后公开展示」 |
| 本地存储 | IndexedDB（库名 `huaxia-visitor-records`），**不登录、不上传、不追踪**；页面显示本机占用/配额 |
| 导出 | 生成 ZIP（`records.json` + `photos/<记录 id>/<照片 id>.jpg` + `README.txt`），**stored 方式**（JPEG 无需压缩） |
| 导入 | 读回 ZIP（同时兼容 deflate 压缩包），校验每张照片 sha256，不符即跳过并提示 |
| 已发布栏目 | 读取 `src/data/visitor-records.json`；每条强制显示「访客投稿 · 未经馆方核验」＋投稿人＋审核日期＋审核备注 |

## 三、审核与发布流程（站长侧）

1. 访客导出 ZIP 并交给你（后续如需后端，可加 Cloudflare R2 + D1 的上传通道，见文末）。
2. 核对三件事：**照片是否本人拍摄**（与访客确认）、**馆方是否允许拍摄**、**画面中是否有人物且已获同意**。
3. 通过后：把该记录的照片放到 `public/visitor-records/<记录 id>/`，在 `src/data/visitor-records.json` 的 `records` 里追加一条：

```json
{
  "id": "<与访客导出中的记录 id 一致>",
  "museumId": "jz",
  "museumName": "荆州博物馆",
  "province": "湖北省",
  "city": "荆州",
  "visitedAt": "2026-09",
  "note": "访客原文（可删改，但不得添加未经核验的鉴定结论）",
  "contributor": "访客署名",
  "publishedAt": "2026-09-30",
  "reviewedAt": "2026-09-30",
  "reviewerNote": "已核对本人拍摄声明与馆方拍摄许可；画面无人物。",
  "photos": [{ "src": "/visitor-records/<id>/<photoId>.jpg", "width": 2048, "height": 1536, "sha256": "…", "caption": "…" }]
}
```

4. `npm run build` → 测试（`visitor-records.test.mjs` 会校验字段、`museumId` 是否真实存在、照片路径前缀）→ 部署。

硬规则（由测试守住）：
- 访客照片**不得**出现在 `src/data/images.json`、故事文本或策展页面；
- 已发布记录必须有 `contributor / publishedAt / reviewedAt / reviewerNote`；
- 照片路径必须在 `/visitor-records/` 下；
- 访客工具代码**不得**出现 `fetch`/`XMLHttpRequest`/`sendBeacon`/`geolocation`，也不得导入舆图数据。

## 四、性能与预算

两个页面各自独立成包：

| 页面 | 入口文件 | 首屏 JS（含静态导入的共享 chunk） |
| --- | --- | --- |
| 舆图 `index.html` | `assets/index-*.js` | **325,312 B**（预算 326,000） |
| 访客页 `visitor-records/index.html` | `assets/visitor-*.js`（25.7 KB） | 218,826 B（React 共享 chunk） |

引入第二个入口后，Rollup 把 React 等共享依赖提到公共 chunk，因此**入口文件本身变小了**（325,695 → 132,229），预算测试也随之改为统计**入口 + 其静态导入图**的合计字节，否则口径会失真（这正是本次修正的一处测试问题）。

访客页在舆图的页脚新增入口链接（`#visitor-link`，与署名同一行），只增加约 60 字节，入口预算仍然满足。

### 本轮修掉的两个真实问题

1. **预算口径失真**：加了第二个入口后 Rollup 把 React 等共享依赖提成公共 chunk，入口文件从 325,695 掉到 132,229，而按原口径的测试只量入口文件——数字"变好"了但含义变了。已把测试改为统计**入口 + 静态导入图**（325,312），并对"访客工具不得进入舆图首屏"加了断言。
2. **导入重复判断的竞态**：导入原按组件状态判断重复记录，若"清空"与"导入"相邻发生，可能拿到过期列表而误判为重复（表现为"新增 0 条，跳过重复 1 条"）。已改为**直接读 IndexedDB 实况**判断，E2E 也改为等待"已清空"完成提示后再导入。

## 六、已知边界与下一步

- **本期没有任何服务端**：记录只在访客自己的浏览器里，你看不到，除非对方导出后发你。若要做成"公网可直接提交"，需要第二阶段（Cloudflare Pages Functions + R2 + D1/KV）：实测本账号 **R2 尚未启用**（`code: 10042 Please enable R2 through the Cloudflare Dashboard`），D1 与 KV 已可用。
- 审核只能人工完成；没有审核机制就不应开放公网提交。
- 若未来把站点搬回国内托管，UGC 会涉及备案与内容审核要求；当前托管在 `pages.dev`（境外），仍建议补一份用户协议与隐私说明。
- 访客页不做器物鉴定：访客写下的"这是什么"一律视为**自述**，不进入任何策展字段。
