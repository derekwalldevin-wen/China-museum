# 设计品质第七轮：拆首屏 JS 构成，把 46KB 的馆藏索引压成 21KB

日期：2026-10-02。上一轮结尾我说要拆解首屏 313KB 的构成。这一轮拆完了，也压掉了一块，但过程里有两次"假设被数据推翻"。

## 一、先拆构成（结果是假设被推翻）

| 分片 | 体积 | 内容（实测） |
| --- | --- | --- |
| `client` | **188.6 KB** | **零汉字**——纯 React 运行时（react-dom + scheduler），不可再挤 |
| `index` | 124.8 KB | 应用代码 + 首屏数据 |

我原本假设"文物卡片文案（223 条）在首屏里"，**核实后是错的：223 条里 0 条在首屏**（早先的标记匹配到了一个通用词，属误报）。这条如果没核实就动手，会白做一轮。

用入口静态 import 图继续追，首屏真正的数据大头是 **`src/data/museum-index.json` 46.1 KB**：59 座馆 + 223 件文物的元数据，其中**文物级字段占 58%（26.6 KB）**。

## 二、改法：浏览器只下载紧凑形式

约束是不能改落盘形状——`museum-index.json` 被 12 个脚本与测试读取。所以：

1. `scripts/generate-museum-data.mjs` **额外**产出一份 `museum-index.compact.json`：键名换成固定字段顺序，馆与文物都变成元组；
2. `src/data/museum-index.ts` 只改这一处：导入紧凑形式并在启动时解码，**导出的数据结构与之前完全一致**（组件、搜索、面板一行没改）；
3. 编码前先核对了字段全集（6 个必需 + 2 个可选，且只有 1 件文物用了可选字段），确保不会静默丢字段。

## 三、效果与一句实话

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 索引文件（可读版，给脚本用） | 46.1 KB | 46.1 KB（不变） |
| 索引文件（紧凑版，给浏览器） | — | **20.8 KB** |
| 线上初始 JS | 313.4 KB | **300.4 KB** |
| 其中 `index` 分片 | 124.8 KB | **111.9 KB** |

**实话**：文件大小对比（46.1 → 20.8 KB）看起来像省了 25KB，实际只省了约 **13KB**（线上 313.4 → 300.4）——因为 esbuild 本来就会把可读 JSON 里重复的键名转成对象标识符，并没有把键名当字符串重复传输。这个差值是我在报告里必须讲清楚的。

## 四、到此为止的边界

首屏 JS 300.4 KB，其中 **188.6 KB 是 React 运行时**（`client` 分片零汉字，纯粹的框架代码）。要继续大幅下降，只能换框架或改架构——**性价比已经不划算**。

所以性能这条线我认为可以收尾了：这一路从 **327.8 KB → 300.4 KB**（首屏 JS），渲染阻塞样式 **133 KB → 68.8 KB**，冷启动 **LCP 2388–4076ms → 72–140ms**，第三方请求 **3 个 → 0 个**。
