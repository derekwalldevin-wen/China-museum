# 实地照片自动入库系统 · 设计（草案 v1）

日期：2026-10-01。状态：设计稿，待你确认投放方式与发布层级后实施。

## 一、目标

你或游客拍了一张博物馆现场照片，系统能：**① 读照片 → ② 识别是哪件文物（给候选+置信度）→ ③ 与站内 206 件在册清单自动对号 → ④ 起草介绍与故事 → ⑤ 人工审核后发布**。

一句话原则：**机器只负责"提出候选与草稿"，"认定"和"发布"必须有人和来源两道关。**

## 二、两条入口（层级不同，规则不同）

| 入口 | 用于 | 图片署名与授权 | 发布位置 |
| --- | --- | --- | --- |
| **策展层** | 你自己拍摄、可确认的照片 | `authorizationStatus: pending`，credit 写明"用户提供 · 拍摄于 X 馆 · 未取得馆方授权" | 可挂到具体文物条目（`images.json` 的 `variants`） |
| **访客层** | 游客提交的照片（第二期已上线） | 投稿人署名 + 审核后公开 | `/visitor-records/`，标「访客投稿 · 未经馆方核验」 |

沿用站内既有先例：`gg-qmsh`《清明上河图》就是"用户提供影像"入库的（`/artifact-sources/user-qingming/…`，授权 pending），流程与字段完全可复用。

## 三、处理流水线（8 步）

1. **投放**：照片放进 `inbox/<馆名>/`（已建好且已 gitignore），或走访客页上传（线上）。
2. **隐私处理**：canvas 重编码，**剥掉 EXIF/GPS**，长边 ≤2048、缩略图 480——这段已在一期实现（`src/visitor/core.ts`），直接复用。
3. **去重**：按 `sha256` 判重，避免同一张图重复入库。
4. **识别（三级证据，强度从高到低）**：
   - **A 级｜展签文字**：照片里带说明牌 → OCR 出的文物名是最强证据；
   - **B 级｜你自己的标注**：文件名/备注里写了名称、馆别、展厅；
   - **C 级｜视觉候选**：我按器形、纹饰、铭文、色泽给 1–3 个候选 + 置信度 + **判断依据**（例如"四龙四凤＋鹿角形底座 → 曾侯乙尊盘"）。
5. **对号入座**：与 206 件在册清单模糊匹配（正名/别名/馆别）。命中 → 挂到该文物；未命中 → 新建**候选条目**（状态：待来源）。
6. **起草介绍与故事**：**只有拿到可达且可读的权威来源才写正文**（这是本项目一直在执行的硬规则）；拿不到就只留"待补"占位，并列出"缺什么证据"。
7. **审核**：走已上线的令牌审核台（`/visitor-records/review/`）→ 通过／驳回（驳回必填理由）。
8. **上线与可回滚**：发布后记 `retiredAssets`／版本记录，任何一步都能退回上一版。

## 四、识别的诚实性规则（写进系统也会写进测试）

1. **视觉识别 = 假设**：我给的候选一律标注"待来源核验"，不能凭照片就把结论写进正文。
2. **不得挪用**：绝不把"另一件相似器物"的报道当成这件的事实（本项目已多次因此放弃来源，例如把"金代山水人物故事镜"的报道拒用于"双鱼纹铜镜"）。
3. **置信度分级**：`确定`（有展签/铭文）/`很可能`（器形纹饰唯一匹配）/`可能`（同类多件）/`未能识别`。
4. **同名多件要分开**：如"同一座墓出土三只蓝瓶"这类情况，必须落到具体一件，不能含糊。

## 五、数据结构（草案）

访客照片记录（在既有 visitor record 上扩展）：

```json
{
  "id": "vp-2026-10-01-0001",
  "museum": "湖北省博物馆",
  "city": "武汉", "province": "湖北",
  "shotAt": "2026-09-30",
  "contributor": "德里克文",
  "photo": { "sha256": "…", "width": 4032, "height": 3024, "exifStripped": true },
  "identification": {
    "status": "confirmed | likely | possible | unknown",
    "artifactId": "hub-ywj",
    "candidates": [{ "artifactId": "hub-ywj", "name": "春秋越王勾践剑", "confidence": 0.9, "basis": "剑身近格处鸟虫书铭文可辨" }],
    "evidenceLevel": "label-ocr | user-note | visual",
    "labelText": "（展签 OCR 原文，如有）"
  },
  "publishing": { "layer": "visitor | curated", "reviewedAt": null, "reviewerNote": null }
}
```

## 六、复用清单（不必从零写）

- 照片压缩/EXIF 剥离：`src/visitor/core.ts`
- 上传、限流、审核、公开接口：`functions/api/visitor/*`（第二期已上线）
- 审核台：`src/visitor/ReviewApp.tsx`
- 文物在册清单匹配：`src/data/museum-index.json`（206 件）
- 图片入库与授权字段：`src/data/images.json`（`variants` + `provenance`）

## 七、实施顺序（建议）

| 阶段 | 内容 | 交付 |
| --- | --- | --- |
| **P1（本轮）** | 你把这批湖北照片放进来，我**逐张人工识别**并列出候选表，你确认后再入库 | 识别清单 + 入库条目 |
| **P2** | 把 P1 的动作脚本化：`scripts/import-photos.mjs`（去重→压缩→写候选 JSON→生成待审条目） | 一条命令批处理 |
| **P3** | 访客侧上线"上传即给候选"：提交后自动跑识别候选，进审核队列（**仍不自动发布**） | 访客自动补全候选 |
| **P4** | 来源可得时自动起草故事骨架（只填有来源的段落，其余留空并标注） | 半自动撰稿 |

## 八、我需要你提供的最小信息

1. 照片文件（放 `inbox/hubei/` 或告诉我路径）；
2. 拍摄馆名（默认按"湖北省博物馆"处理）；
3. 拍摄日期（可留空）；
4. 是否允许**公开展示并在图上署名**"摄影：德里克文"；
5. 发布层级：只放访客层（保守）／也允许挂到文物条目（策展层）。

> 说明：湖北馆目前在册 5 件——**战国曾侯乙编钟（hub-zhy）、春秋越王勾践剑（hub-ywj）、战国曾侯乙尊盘（hub-zp）、睡虎地秦简《秦律十八种》（hub-qj）、元青花四爱图梅瓶（hub-sat）**。若你的照片是这 5 件之一，可立即挂进对应条目；若是馆内其他名品（如彩绘乐舞图鸳鸯形盒、十六节龙凤玉挂饰、崇阳铜鼓等），则先作为"新候选条目"，等拿到权威来源再写故事。
