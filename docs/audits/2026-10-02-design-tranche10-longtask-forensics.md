# 设计品质第十轮：把上一轮的"线上长任务"查到底——结论是**我的测量方式错了**

日期：2026-10-02。上一轮结尾我记下"线上 2 个长任务（最长 170ms）待查"。这一轮查完了，**结论是：那不是网站的问题，是我的指标没归因。**

## 一、对照实验：四种情形全是 0 长任务

假设：长任务来自**图片解码**（故事首图 detail 图较大）。设计对照实验——**图片仍在下载时交互** vs **图片已解码后交互**，本地（含 Slow 4G 限速）与线上各跑一遍：

| 环境 | 交互时图片状态 | 长任务 |
| --- | --- | --- |
| 本地（Slow 4G） | 未就绪 | **0 个** |
| 本地（Slow 4G） | 已解码 | **0 个** |
| 线上 | 未就绪 | **0 个** |
| 线上 | 已解码 | **0 个** |

假设被推翻：**图片不是原因，四种情形都没有长任务。**

## 二、真正的原因：指标没有"归因到交互"

上一轮的写法是"清空采样 → 点击 → 取窗口内全部长任务"。问题在于：清空之后，**页面自身的后台工作**（延迟预取、provenance 请求的回调、GC）也会落进这个窗口，被算成"交互卡顿"。审计脚本连续做了多次导航与点击，后台恰好有活干，于是偶发出现 2 个 170ms。

**修法（改指标，不改代码）**：把长任务**归因到点击时间窗**——只统计"点击后 250ms 内启动"的长任务，与点击无关的后台任务不计入；同时把"全页长任务最长值"作为参考值保留在判据文案里。

修完后连测：

| 环境 | 归因长任务 | 全页长任务 |
| --- | --- | --- |
| 本地 | **0 个** | 0 个 |
| 线上第 1 次 | **0 个** | 0 个 |
| 线上第 2 次 | **0 个** | 0 个 |

线上自检 **100/100**（15 个维度全满分）。

**我要明确说清**：这一轮**没有找到性能缺陷**，上一轮那个警报是我的测量方式的锅。比起顺手做个"优化"把指标糊过去，我更愿意把这句话写在文档里。

## 三、顺手把"一致性"维度做实

量了阅读面的设计 token：

| 项目 | 实测 | 判断 |
| --- | --- | --- |
| 圆角 | **0 种**（全直角） | 刻意的刻本版式 ✓ |
| 阴影 | 2 种（其中一种是透明的空阴影） | 收敛 ✓ |
| 描边宽度 | 1px×19 + 一处刻意的 3px 红色顶线 | 收敛 ✓ |

于是把"一致性"从"只看间距"扩成三项：间距 4px 基准（2 分）＋ 圆角取值 ≤2 种（1 分）＋ 阴影取值 ≤2 种（1 分）。
